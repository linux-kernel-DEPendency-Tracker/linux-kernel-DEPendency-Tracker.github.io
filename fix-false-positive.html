A DEPT false positive, and how it was fixed
commit fd560f665f3e "rcu/update: fix same dept key collision between various types of RCU"

Written for someone who has just enabled CONFIG_DEPT and got a scary report. Everything below is taken from this tree (branch dept19.1_v7.2).

TL;DR

DEPT reported a circular dependency between cpu_hotplug_lock and "an RCU grace-period wait". It was not real. Two different waits, a synchronize_rcu() and a synchronize_rcu_tasks_trace() were being filed under one DEPT class, because both of them block inside the same function (__wait_rcu_gp()) and DEPT derived the class from that single code location. Merging two unrelated wait channels into one class merged their dependencies too, which closed a cycle that cannot happen in reality.

The fix does not touch any locking. It gives each _wait_rcu_gp() expansion site its own struct dept_key, hands it down to __wait_rcu_gp(), and attaches it to each struct rcu_synchronize’s completion with the new init_completion_dmap() API. Normal RCU and tasks-trace RCU then live in separate classes and the fake cycle disappears.

1. DEPT in 90 seconds

Lockdep tracks lock acquisition order. DEPT tracks wait → event order, so it can also reason about things that are not locks: folio locks, completions, waitqueues, DMA fences, grace periods. Its whole model is three markers, which is exactly what a report prints:

MarkerMeaningTypical source
[S]Start of the event context, the point after which this context is responsible for producing an event (e.g. it just took a lock, so it now owes an unlock) mutex_lock(), dept_ecxt_enter()
[W]The Wait that blocked, inside that event context folio_wait_bit_common(), wait_for_completion*()
[E]The Event that is therefore not reachable while the wait is stuck mutex_unlock(), complete()/try_to_wake_up()

One line of a report reads lock(&ni->ni_lock:0) or __wait_rcu_gp(<sched>:0). The parenthesis is the class and the number after : is the subclass. Three objects matter, and confusing them is the single most common reason a beginner cannot tell a false positive from a real bug:

ObjectWhat it isWhere
struct dept_keyClass identity. Two waits with the same key are the same class, i.e. DEPT believes they are the same synchronization channel. include/linux/dept.h
struct dept_mapInstance state (name, subclass, wgen timestamp) pointing at a key. Many maps may share one key. include/linux/dept.h
dependency graphEdges between classes, accumulated over the whole boot. A cycle here is what gets reported. kernel/dependency/dept.c, /proc/dept_deps

The one rule to remember

DEPT only ever compares classes. If you give two unrelated waits the same key, DEPT will happily combine a dependency observed on one with a dependency observed on the other. Key granularity is the correctness knob for false positives.

2. How a wait_for_completion() gets its class

This is the mechanism the bug lives in. In this tree struct completion holds a pointer to an optional map (include/linux/completion.h):

struct completion {
	unsigned int done;
	struct swait_queue_head wait;
	struct dept_map *dmap;          /* NULL by default */
};

#define init_completion(x) init_completion_dmap(x, NULL)

#define wait_for_completion_state(x, s)					\
({									\
	int __ret;							\
	sdt_might_sleep_start_timeout((x)->dmap, -1L);			\
	__ret = __wait_for_completion_state(x, s);			\
	sdt_might_sleep_end();						\
	__ret;								\
})

and include/linux/dept_sdt.h decides the key:

#define sdt_might_sleep_start_timeout(m, t)				\
	do {								\
		struct dept_map *__m = m;				\
		static struct dept_key __key;				\
		dept_stage_wait(__m, __m ? NULL : &__key, _THIS_IP_, __func__, t);\
	} while (0)
  • No map (x->dmap == NULL): the class is that static __key one key per place in the code where the wait happens. The report prints the class as <sched> because the wait was staged for the scheduler (dt->stage_sched_map = true in dept_stage_wait()).
  • With a map: the map’s key wins, so the caller chooses the granularity.

The matching event is not annotated in complete() at all. DEPT discovers it in try_to_wake_up():

waiter task                                     waker task
-----------                                     ----------
wait_for_completion_state(&rs->completion)
  sdt_might_sleep_start_timeout(dmap, -1)
    dept_stage_wait(m, k, ...)   ── stages the class on the task
  __wait_for_completion_state()
    schedule()                                  complete(&rs->completion)
      dept_request_event_wait_commit()            swake_up...  -> try_to_wake_up(p)
      (the wait becomes real)                        dept_ttwu_stage_wait(p, ip)
                                                       __dept_event(p's staged map,
                                                                    "try_to_wake_up")

So whoever wakes the sleeper is retroactively credited as the producer of that class’s event. That is why the report says [E] try_to_wake_up(<sched>:0) and prints an extra "(wait to wake up)" stack: the stack of the task that was waiting.

4. Why it is a false positive

The two <sched> occurrences are not the same channel. Both call chains funnel into the very same function, and that function is where the static struct dept_key __key lived:

   synchronize_rcu()                       synchronize_rcu_tasks_trace()
     synchronize_rcu_normal()                synchronize_rcu_tasks_generic()
       _wait_rcu_gp(...)                       wait_rcu_gp_state(...) -> _wait_rcu_gp(...)
          \                                       /
           \_____________  __wait_rcu_gp()  ______/
                                 |
                    wait_for_completion_state(&rs_array[i].completion, state)
                                 |
                     sdt_might_sleep_start_timeout(NULL, -1L)
                                 |
                     one static __key  ==  ONE DEPT CLASS  ==  "<sched>"
flowchart TD SR["synchronize_rcu()"] --> SRN["synchronize_rcu_normal()"] ST["synchronize_rcu_tasks_trace()"] --> STG["synchronize_rcu_tasks_generic()"] SRN --> WG["_wait_rcu_gp()"] STG --> WG WG --> WRG["__wait_rcu_gp()"] WRG --> WFC["wait_for_completion_state()"] WFC --> K["static dept_key inside __wait_rcu_gp ONE class"] K --> C1["edge recorded: cpu_hotplug_lock to this class"] K --> C2["edge recorded: this class to cpu_hotplug_lock"] C1 --> CYC["cycle reported"] C2 --> CYC

Before: every RCU flavour funnels through one wait callsite, so unrelated edges land on one graph node and close a loop.

flowchart TD SR["synchronize_rcu()"] --> SRN["synchronize_rcu_normal()"] ST["synchronize_rcu_tasks_trace()"] --> STG["synchronize_rcu_tasks_generic()"] SRN --> K1["_wait_rcu_gp() expansion static dept_key 1"] STG --> K2["_wait_rcu_gp() expansion static dept_key 2"] K1 --> M1["rcu_synchronize.dmap class: normal RCU GP"] K2 --> M2["rcu_synchronize.dmap class: tasks RCU GP"] M1 --> E1["edge: cpu_hotplug_lock to class 1"] M2 --> E2["edge: class 2 to cpu_hotplug_lock"] E1 --> NO["no cycle"] E2 --> NO

After fd560f665f3e: the key is created per macro expansion site and carried into each rcu_synchronize’s map, so the two flavours are different classes.

Before one class, fake cycle

        cpu_hotplug_lock
            ^        |
   waits    |        |  waits
   (tasks-  |        v  (normal RCU GP)
   trace    |   <sched>:0
   kthread) |   [merged class]
            +--------+
        CYCLE  =>  reported

edges actually observed:
  cpu_hotplug_lock -> <sched>   (from synchronize_rcu, ctx A)
  <sched> -> cpu_hotplug_lock   (from rcu_tasks kthread, ctx B)
different channels, same node.

After two classes, no cycle

        cpu_hotplug_lock
            |              ^
     waits  |              | waits
            v              |
    <rcu-normal GP>   <rcu-tasks GP>
       class K1            class K2

  cpu_hotplug_lock -> K1
  K2 -> cpu_hotplug_lock
  NO cycle  => silent

Why is the merge wrong even though both really are "wait for a grace period"?

  • They are woken by different machinery: normal RCU’s callback path vs. the rcu_tasks kthread. Blocking one never blocks the other.
  • The rcu_synchronize objects are distinct on-stack objects, and the tasks-trace wait in the report belongs to a boot-time initcall (rcu_init_tasks_generic()), which cannot be in a cycle with a running cgroup write.
  • Both cpu_hotplug_lock takers in the report are readers (cpus_read_lock()); the "A→B" edge in context A only exists because percpu_down_write() comes later. Even ignoring that, the cycle needs the two <sched> nodes to be one node and they are not.

5. The fix

git show fd560f665f3e 3 files, 12 insertions, 7 deletions. No locking change.

5.1 Give every _wait_rcu_gp() expansion its own key

--- a/include/linux/rcupdate_wait.h
+++ b/include/linux/rcupdate_wait.h
 struct rcu_synchronize {
 	struct rcu_head head;
 	struct completion completion;
 	struct rcu_gp_oldstate oldstate;
+	struct dept_map dmap;
+	struct dept_key dkey;
 };

 void __wait_rcu_gp(bool checktiny, unsigned int state, int n, call_rcu_func_t *crcu_array,
-		   struct rcu_synchronize *rs_array);
+		   struct rcu_synchronize *rs_array, struct dept_key *dkey);

 #define _wait_rcu_gp(checktiny, state, ...)					\
 do {										\
 	call_rcu_func_t __crcu_array[] = { __VA_ARGS__ };			\
+	static struct dept_key __key;						\
 	struct rcu_synchronize __rs_array[ARRAY_SIZE(__crcu_array)];		\
-	__wait_rcu_gp(checktiny, state, ARRAY_SIZE(__crcu_array), __crcu_array, __rs_array);
+	__wait_rcu_gp(checktiny, state, ARRAY_SIZE(__crcu_array), __crcu_array, __rs_array, &__key);
 } while (0)

_wait_rcu_gp() is a macro, so static struct dept_key __key is instantiated once per expansion site one in synchronize_rcu_normal() (kernel/rcu/tree.c:3314, via wait_rcu_gp()), one in synchronize_rcu_tasks_generic() (kernel/rcu/tasks.h:672, via wait_rcu_gp_state()), one per synchronize_rcu_mult() user, and so on. That is the granularity that was missing: previously the only static existed inside the callee.

5.2 Attach the key to each wait through a real map

--- a/kernel/rcu/update.c
+++ b/kernel/rcu/update.c
 		if (j == i) {
 			init_rcu_head_on_stack(&rs_array[i].head);
-			init_completion(&rs_array[i].completion);
+			sdt_map_init_key(&rs_array[i].dmap, dkey);
+			init_completion_dmap(&rs_array[i].completion, &rs_array[i].dmap);
 			(crcu_array[i])(&rs_array[i].head, wakeme_after_rcu);
 		}
--- a/kernel/rcu/rcu.h        +#include <linux/dept_sdt.h>

Now wait_for_completion_state() sees a non-NULL ->dmap, so sdt_might_sleep_start_timeout() stages that map, and dept_stage_wait()/dept_map_reinit() keep the map’s key (dept_map_reinit() only replaces ->keys when a key is passed, and here k == NULL because m != NULL). Result: per-flavour class, per-object map.

5.3 Why not simply let each rcu_synchronize have its own class?

dept_map_init(m, NULL, ...) would use &m->map_key, i.e. a class per object. Every synchronize_rcu() allocates rs_array[] on the stack, so each call would create a brand-new class, no dependency would ever accumulate across calls, and DEPT would go blind on RCU. The right granularity for a synchronization channel is per-callsite (shared across invocations), which is what the patch does.

Two honest caveats about this patch (verified in the tree)

  • rcu_tasks, rcu_tasks_rude and rcu_tasks_trace all reach wait_rcu_gp_state() through the single expansion in synchronize_rcu_tasks_generic() (kernel/rcu/tasks.h:672), so those three flavours still share one key. The reported collision (normal RCU vs. tasks-trace RCU) is gone; a collision among the tasks flavours is still possible and would need the key to be pushed into struct rcu_tasks.
  • The new struct rcu_synchronize::dkey field has no user: grep -rn '\.dkey\|->dkey' kernel/ include/ only matches lockdep’s own lock_class_key::dkey. The class comes from the caller-site key, not from this field.

6. The general process for fixing a DEPT false positive

Nothing below is RCU-specific; this is the routine to follow for any report. DEPT’s Kconfig help says it plainly: "This feature is considered EXPERIMENTAL that might produce false positive reports because new dependencies start to be tracked, that have never been tracked before." Multiple reports are allowed, so a false positive does not silence the tool.

  1. Read only the summary first. Write the two (or more) contexts down as [S] / [W] / [E] triples. Each context yields one edge: "while inside the event context of class X, we waited for class Y" ⇒ edge X → Y. A report is just a cycle over those edges.
  2. Identify each class’s origin. This is the decisive step. 
    class printed as          means                                    key comes from
------------------------  --------------------------------------   -----------------------------
&foo->bar:0               a named map (lock or explicit dept_map)  that lock/map's key
<sched>:0                 a schedule()-based wait with NO map      static key at the WAIT callsite
(unknown)(...)            event context start not recorded         n/a  (N/A stack)
    <sched> and "(unknown)" are the smell of a coarse class. Find the wait callsite from the [W] stack, open that function, and ask: do semantically different wait channels pass through this exact line? If yes, you have a key collision, the case fixed by fd560f665f3e.
  3. Prove the two contexts can actually coexist. Check for: boot-time-only code (initcalls), single-threaded phases, one-shot objects, readers vs. writers of the same rwsem, and timeout waits (a wait with a timeout cannot deadlock forever that is why DEPT ignores them unless CONFIG_DEPT_AGGRESSIVE_TIMEOUT_WAIT=y). If they cannot coexist, the cycle is theoretical.
  4. Confirm with the graph, not with intuition. 
    grep -i dept /proc/dept_stats        # objects in use, reports so far
cat /proc/dept_deps                  # every class-to-class edge DEPT has recorded
    Look for the suspect class appearing with edges from unrelated subsystems that is a merged class in plain sight.
  5. Choose the smallest correct fix using this decision tree: 
    Is the reported cycle physically possible?
├─ YES  -> it is a real bug. Fix the code, not the annotation.
└─ NO
   ├─ Do unrelated waits share one class?
   │    ├─ same callsite, different channels
   │    │     -> move the key OUT to where the channels differ
   │    │        (macro-level `static struct dept_key`, or a key
   │    │         field in the per-channel struct) and pass it down.
   │    │        APIs: sdt_map_init_key(map, key)
   │    │              init_completion_dmap(completion, map)
   │    └─ same channel, but instances must not be conflated
   │          -> use a subclass: dept_map_init(m, k, sub_u, n)
   │             (sub_u < DEPT_MAX_SUBCLASSES_USR)
   ├─ Is the wait/event annotation itself wrong or too strong?
   │    -> fix the annotation site (e.g. weaker/narrower
   │       sdt_might_sleep_* scope; cf. "cpu/hotplug: use a weaker
   │       annotation in AP thread" in this tree)
   └─ Is the object genuinely un-analysable?
        -> last resort: make the map nocheck (lockdep's
           no-validate key), and say why in the changelog.
  6. Verify. Rebuild with CONFIG_DEPT=y, boot, re-run the reproducer, and check two things: the report is gone, and DEPT still reports the deadlocks you expect. This branch ships CONFIG_DEPT_UNIT_TEST (kernel/dependency/dept_unit_test.c) for the second half; the lkdtm folio-lock deadlock scenarios live on the side branch b4/dept19.1_v7.2/rdtm. Losing detection while silencing noise is the classic regression in the hugetlb thread quoted in the companion document, the DEPT author found that his own false-positive suppression (tc->reported in print_circle()) had also suppressed a genuine report.
  7. Write the changelog like the commit you are reading. State the two call chains that collided, paste the report, and say which key/map granularity you changed. That is what makes a DEPT patch reviewable.

API cheat sheet (this tree)

APIEffect on class granularity
sdt_map_init(m)Static key at this code location; all instances initialized here share one class.
sdt_map_init_key(m, k)Caller supplies the key ⇒ caller controls granularity. Used by the RCU fix.
dept_map_init(m, NULL, sub_u, n)Per-instance class (&m->map_key). Beware: short-lived objects then never accumulate dependencies.
init_completion_dmap(x, m)Attach an explicit map to a completion; otherwise the class is the wait_for_completion*() callsite.
sdt_might_sleep_start[_timeout](m, t) / sdt_might_sleep_end() Marks a "might block in schedule()" region; with m == NULL the callsite key is used.
sdt_wait(m) / sdt_event(m) / sdt_ecxt_enter/exit(m) Explicit wait/event annotation for custom primitives.
CONFIG_DEPT_AGGRESSIVE_TIMEOUT_WAITOff by default: timeout waits are not tracked, since they cannot deadlock forever.
