1. Why lockdep is not enough

Lockdep validates lock acquisition order. It works because a lock is acquired and released by the same context, so "A then B" is a meaningful statement about one task.

Plenty of kernel blocking does not fit that shape. A folio lock is set by one context and cleared by another. A wait_for_completion() is satisfied by a kthread. A DMA fence is signalled by an IRQ. Lockdep has no order to check there, so it stays silent and real deadlocks ship. Both case studies below are exactly that: silent deadlocks that lockdep structurally cannot see.

DEPT (DEPendency Tracker, by Byungchul Park) changes the primitive being tracked, from "lock order" to "wait → event". A lock becomes just one special case: "wait for the unlock event". The documentation in this tree (Documentation/dev-tools/dept.rst) puts it as:

"A deadlock occurs when one or more contexts are waiting for events that will never happen. If an event occurrence to awaken its wait is a prerequisite to reaching another event, we call it dependency. A circular dependency of events leads to a deadlock."

2. The DEPT model: wait, event, class

2.1 One context records one dependency

Inside a context, a wait that happens after the context has started owing an event creates a dependency: the owed event cannot happen until the wait is satisfied.

flowchart TD S["Context"] --> W["Wait B"] W --> E["Event A"] E -. "dependency: A cannot happen until B is resolved" .-> W

Read: "this context must see event B before it can produce event A", i.e. edge A → B.

2.2 A dependency spans contexts

The waiter and the producer of an event are usually different contexts. That is exactly the part lockdep cannot model, and the part DEPT is built for.

flowchart TD subgraph X["Context X"] direction TB RA["Request event A"] --> WA["[W] Wait A"] end subgraph Y["Context Y"] direction TB S["[S] Start of event A's context"] --> WB["[W] Wait B"] WB --> EA["[E] Event A"] end RA --> S EA -. "wakes X" .-> WA

X waits for A; Y is the one that will produce A, but Y first blocks on B. So X’s progress now depends on B as well.

2.3 A cycle is a deadlock

flowchart LR A(("A")) --> B(("B")) B --> C(("C")) C --> A

DEPT accumulates these edges between classes for the whole boot and reports the moment a new edge closes a loop.

A context that is inside an "event context" and blocks creates one graph edge:

┌─────────────────────── context ──────────────────────────────┐
│  [S] start owing event A   (e.g. mutex_lock → owes unlock)   │
│        ...                                                   │
│  [W] block waiting for event B   (e.g. folio_lock)           │
│        ...                                                   │
│  [E] event A would happen here but is unreachable            │
└──────────────────────────────────────────────────────────────┘

                   edge: A depends on → B

Two such edges pointing at each other = cycle = deadlock report.

Three nouns, and beginners must keep them apart:

TermMeaning
waitA blocking point. Annotated by the primitive (sdt_wait(), sdt_might_sleep_start(), dept_wait()).
eventThe thing that unblocks that wait: an unlock, a folio_unlock(), a complete(), a try_to_wake_up().
classThe identity DEPT compares. Derived from a struct dept_key. The graph is a graph over classes, not over objects. This is why class granularity decides whether a report is true or noise.

3. How to read a report

Every report starts with a summary that is the whole story; the detail sections are just the stacks behind each line.

SymbolReport textHow to read it
[S]start of the event context "From here on, this context owes event X to someone."
[W]the wait blocked "And here it went to wait state(e.g., sleep) while waiting for Y."
[E]the event not reachable "So, X is impossible while the context is waiting for the event."

Every report you will ever read has this shape, two contexts, each stuck before its own [E]:

flowchart TD subgraph A["Context A"] direction TB AS["[S] Start or acquire A"] AW["[W] Wait for B"] AE["[E] End or release A"] AS --> AW --> AE end subgraph B["Context B"] direction TB BS["[S] Start or acquire B"] BW["[W] Wait for A"] BE["[E] End or release B"] BS --> BW --> BE end AW -. "requires B [E]" .-> BE BW -. "requires A [E]" .-> AE

The generic DEPT deadlock: neither context can reach its [E], because each [W] depends on the other context’s [E].

  • [S] Start: the context acquires or starts owning a resource, so it now owes the matching event.
  • [W] Wait: the context waits for another resource or event.
  • [E] End / Event: the context releases the resource or emits the event. If it is unreachable, everyone waiting on it is stuck.

Notation: lock(&ni->ni_lock:0) is class(:subclass). (unknown) or an (N/A) stack means DEPT knows the class but not the code location, normal for the event side of things like folio locks and completions, where the producer is discovered dynamically. Do not treat (N/A) as "bug in DEPT".

4. Turning it on

CONFIG_DEPT=y                            # lib/Kconfig.debug: "Dependency tracking (EXPERIMENTAL)"
                                         # selects PROVE_LOCKING, STACKTRACE, KALLSYMS_ALL, ...
CONFIG_DEPT_AGGRESSIVE_TIMEOUT_WAIT=n    # default: ignore waits that have a timeout
CONFIG_DEPT_UNIT_TEST=m                  # optional self-test of the tracker

/proc/dept_stats                         # internal object usage / report counters
/proc/dept_deps                          # every class-to-class edge recorded so far

Unlike lockdep, DEPT keeps going after the first report ("Multiple reports are allowed if there are more than a single problem"), which matters while the tracker is still shaking out false positives.

5. Case study (1) ntfs3: ni_lock vs. PG_locked

syzbot bed15dbf10294aa4f2ae, "INFO: task hung in do_user_addr_fault" · analysed by Linus Torvalds and Tetsuo Handa, Jan 2023 · reproduced by DEPT by Byungchul Park · fixed by commit 0226635c304c (v6.2).

5.1 The bug

Two threads, one file. Nobody violates a lock order, because only one of the two blocking objects is a lock.

Context A: truncate (creat(2) → do_truncate)                    Context B: read/write via page cache
--------------------------------------------                    ------------------------------------
ntfs3_setattr
  ntfs_truncate
    ni_lock(ni)  [S]
                                                                filemap_read
                                                                  filemap_get_pages
                                                                    filemap_update_page
                                                                      folio_trylock()  → sets PG_locked  [S]
                                                                      filemap_read_folio
                                                                        mpage_read_folio
                                                                          do_mpage_readpage
                                                                            ntfs_get_block_vbo
                                                                              attr_data_get_block
                                                                                ni_lock(ni)  → blocks   [W]
    truncate_setsize
      truncate_pagecache
        truncate_inode_pages_range
          folio_lock() → waits PG_locked  [W]
                                    ← deadlock: each holds what the other waits for

Lockdep sees only ni_lock; the other half of the cycle is a page flag with no lockdep annotation. Tetsuo’s summary in the thread: "Since no lockdep annotation is used for e.g. PG_locked bit, this deadlock cannot be detected by lockdep..."

sequenceDiagram autonumber participant A as Context A: truncate participant NI@{ "type": "entity", "alias": "ni_lock" } participant FL@{ "type": "entity", "alias": "folio / PG_locked" } participant B as Context B: page-cache read A->>NI: [S] ni_lock(ni) taken in ntfs_truncate B->>FL: [S] folio_trylock() sets PG_locked in filemap_update_page B->>NI: [W] ni_lock(ni) in attr_data_get_block BLOCKS Note over NI,B: B sleeps until A's [E] ni_unlock B-->>FL: [E] folio_unlock unreachable A->>FL: [W] folio_lock() in truncate_inode_pages_range BLOCKS Note over A,FL: A sleeps until B's [E] folio_unlock A-->>NI: [E] ni_unlock unreachable rect rgb(74, 27, 30) Note over A,B: ***DEADLOCK*** Context A's [E] ni_unlock and B's [E] folio_unlock are both unreachable end

*** DEADLOCK ***  A holds ni_lock and waits for the folio  ·  B holds the folio and waits for ni_lock

Real runtime order, one row per step: A already holds ni_lock when B grabs the folio, and each then blocks on what the other holds. Dependency cycle: ni_lock → folio lock → ni_lock.

Context A cannot reach [E] unlock(ni_lock) until Context B performs [E] folio_unlock; Context B cannot reach [E] folio_unlock because it is blocked at [W] lock(ni_lock).

5.2 What DEPT printed

*** DEADLOCK ***

context A: truncate
    [S] lock(&ni->ni_lock:0)                        ntfs3_setattr+0x54b
    [W] folio_wait_bit_common(PG_locked_map:0)      truncate_inode_pages_range+0x9b0
    [E] unlock(&ni->ni_lock:0)                      (N/A)

context B: page-cache read
    [S] (unknown)(PG_locked_map:0)                  (N/A)   ← folio_trylock(), no stack kept
    [W] lock(&ni->ni_lock:0)                        attr_data_get_block+0x32c
    [E] folio_unlock(PG_locked_map:0)               generic_write_end+0xf2

Two edges, one cycle:

  • A: ni_lock’s unlock is unreachable because A waits for PG_locked to clear ⇒ ni_lock → PG_locked.
  • B: folio_unlock() is unreachable because B waits for ni_lock ⇒ PG_locked → ni_lock.

This is the report that Documentation/dev-tools/dept.rst now uses as its worked example, and it is a genuine, reproducible deadlock, a good first report to study precisely because it is true.

5.3 The fix that landed

0226635c304c "fs/ntfs3: don't hold ni_lock when calling truncate_setsize()" Tetsuo Handa, co-developed with Hillf Danton, debugged by Linus, applied directly by Linus for v6.2. Two lines moved, no new locking.

--- a/fs/ntfs3/file.c
+++ b/fs/ntfs3/file.c
@@ -390,10 +390,10 @@ static int ntfs_truncate(struct inode *inode, loff_t new_size)
 	new_valid = ntfs_up_block(sb, min_t(u64, ni->i_valid, new_size));

-	ni_lock(ni);
-
 	truncate_setsize(inode, new_size);

+	ni_lock(ni);
+
 	down_write(&ni->file.run_lock);

Before cycle exists

   ni_lock ──────────────> PG_locked
      ^                        |
      |                        |
      +────────────────────────+
   (truncate waits on folio    (reader holds folio
    while holding ni_lock)      lock, wants ni_lock)

ntfs_truncate:
   ni_lock(ni)                [S]
   truncate_setsize(...)      [W] folio_lock
   ...
   ni_unlock(ni)              [E] unreachable

After edge removed

   ni_lock                PG_locked
      (no edge)   ──────>    ni_lock
                             (one edge only)

ntfs_truncate:
   truncate_setsize(...)      folio_lock taken and
                              released with NO ni_lock held
   ni_lock(ni)                [S] after the page-cache work
   ...
   ni_unlock(ni)              [E] reachable

One direction of the dependency is gone,
so no cycle can be built.

Is it still fixed today?

flowchart LR PG["folio lock (PG_locked)"] --> NI["ni_lock"]

After 0226635c304c only this single direction remains a reader holding the folio lock may still wait for ni_lock, but nothing waits for the folio lock while holding ni_lock. No cycle can be closed.

Yes, and the shape survived a refactor. In this tree the truncate path in fs/ntfs3/file.c is:

		if (newsize != oldsize) {
			truncate_setsize(inode, newsize);      /* page-cache work first, no ni_lock */

			err = ntfs_set_size(inode, newsize);   /* takes ni_lock internally */

The invariant to preserve in ntfs3 is: never call into page-cache truncation while holding ni_lock.

Bonus: this case is now a first-class DEPT citizen

PG_locked is tracked by DEPT upstream in this tree (dept: track PG_locked with dept). See include/linux/pagemap.h: dept_page_set_bit(&folio->page, PG_locked) on the acquire side and dept_page_wait_on_bit(&folio->page, PG_locked) in folio_lock() / folio_wait_locked(). Additionally, The patch "lkdtm: Add folio_lock deadlock scenarios", which turns this exact pattern into an on-demand test; it is not on the dept19.1_v7.2 branch itself.

6. Case study (2) hugetlb: folio lock vs. hugetlb_fault_mutex_table

Reported by Gavin Guo (Igalia), May 2025, found with an internal syzkaller reproducer and a bpftrace script, not by any static checker. Andrew Morton asked on-list whether DEPT would have caught it; after one extra annotation it did. Fixed upstream by 2ae1ab9934c7 (v6.17), Oscar Salvador.

6.1 The bug, a true ABBA, but one side is a folio lock


Context A: hugetlb_wp                                           Context B: filemap_lock_hugetlb_folio
---------------------                                           -------------------------------------
hugetlb_fault
  mutex_lock(B)                    [S]
  filemap_lock_hugetlb_folio
    folio_lock(A)                  [S]
  hugetlb_wp
    mutex_unlock(B)      ← B released, A still held
    ...                                                         hugetlb_fault
                                                                  mutex_lock(B)              [S] (gets it)
                                                                  filemap_lock_hugetlb_folio
                                                                    folio_lock(A)  → blocks [W]
    unmap_ref_private
    ...
    mutex_lock(B)  -> blocks       [W]  ← Context A waits B (held by Context B), Context B waits A (held by Context A)

The window is opened deliberately: hugetlb_wp() must drop the fault mutex and the VMA lock before unmap_ref_private(), but it keeps the pagecache folio locked across that window. Lockdep cannot help, since A is a folio lock.

sequenceDiagram autonumber participant CA as Context A: hugetlb_wp participant F@{ "type": "entity", "alias": "pagecache folio lock" } participant M@{ "type": "entity", "alias": "mutex_table[hash]" } participant CB as Context B: filemap_lock_hugetlb_folio CA->>F: [S] folio_lock(A) taken in filemap_lock_hugetlb_folio CB->>M: [S] mutex_lock(B) taken CB->>F: [W] folio_lock(A) BLOCKS Note over F,CB: Context B sleeps until Context A's [E] folio_unlock CB-->>M: [E] mutex_unlock unreachable CA->>M: [W] mutex_lock(B) after unmap_ref_private BLOCKS Note over CA,M: Context A sleeps until Context B's [E] mutex_unlock CA-->>F: [E] folio_unlock unreachable rect rgb(74, 27, 30) Note over CA, CB: ***DEADLOCK*** Contex A's [E] mutex_unlock and B's [E] folio_unlock are both unreachable end

*** DEADLOCK ***  Context A holds folio A and waits for mutex B  ·  Context B holds mutex B and waits for folio A

Real runtime order. Step 1 is what makes this reachable: Context A hands the mutex away but keeps the folio locked, so Context B can complete steps 2–3 before Context A arrives at step 4. Dependency cycle: folio lock → fault mutex → folio lock.

Context A cannot reach [E] folio_unlock because it is blocked at [W] lock(fault_mutex) (the re-take after unmap_ref_private()); Context B cannot reach [E] unlock(fault_mutex) because it is blocked at [W] folio_lock. Same shape as the ntfs3 cycle, with the two roles swapped.

6.2 Making DEPT see it

DEPT was initially silent on the reproducer. Byungchul’s reply identified two reasons and both are instructive for beginners:

  1. Missing annotation on the fast path. folio_lock() only annotated the slow path, so a wait that came in through the fast path was never staged. The debug patch added dept_page_wait_on_bit(&folio->page, PG_locked) directly in folio_lock() which is what the current tree does permanently.
  2. Report de-duplication hid it. Removing tc->reported = true keep reporting. His own words:
    3. "Some of my efforts to suppress false positives, suppressed the real one."
With those in place, Gavin re-ran the reproducer and DEPT printed the cycle in the first round:

** DEADLOCK ***

context A: hugetlb_wp                               ← the process that holds the folio lock
   [S] (unknown)(pg_locked_map:0)                  (N/A)
   [W] lock(&hugetlb_fault_mutex_table[i]:0)       hugetlb_wp+0xfa4      (re-take after unmap)
   [E] dept_page_clear_bit(pg_locked_map:0)        hugetlb_fault+0x1ccb  (folio_unlock)

context B: filemap_lock_hugetlb_folio               ← the process that holds the mutex
   [S] lock(&hugetlb_fault_mutex_table[i]:0)       hugetlb_fault+0x3c6
   [W] dept_page_wait_on_bit(pg_locked_map:0)      hugetlb_fault+0x817   (folio_lock)
   [E] unlock(&hugetlb_fault_mutex_table[i]:0)     (N/A)

Same two-edge structure as the ntfs3 case, with the roles of "lock" and "page flag" swapped: PG_locked → fault_mutex from A, fault_mutex → PG_locked from B.

6.3 The fix that landed

Gavin’s first patch was the minimal one: drop and re-acquire the pagecache folio lock around the unmap window. Andrew queued it but called it out, "The fix looks a bit nasty… a more broadly architected solution may be needed going forward." That is what happened: the code in this tree carries Oscar Salvador’s rework instead, and no commit in this repository ever adds a folio_unlock(pagecache_folio) to the unmap window.

2ae1ab9934c7 "mm,hugetlb: change mechanism to detect a COW on private mapping" (v6.17) Reported-by: Gavin Guo, Fixes: 40549ba8f8e0, Suggested-by: Peter Xu. 34 insertions, 54 deletions.

The insight is that the folio lock was never needed for the actual question being asked. hugetlb_wp() looked up and locked the pagecache folio only to compare it with the mapped folio, in order to learn "was the reservation for this address already consumed?". That is answerable locally:

-	if (is_vma_resv_set(vma, HPAGE_RESV_OWNER) &&
-			old_folio != pagecache_folio)
+	if (is_vma_resv_set(vma, HPAGE_RESV_OWNER) &&
+	    folio_test_anon(old_folio))
 		cow_from_owner = true;

With the comparison gone, everything around it goes too: the pagecache_folio parameter, the filemap_lock_hugetlb_folio() call in hugetlb_fault(), and all its unlock/put paths. The folio lock is now taken only for the CoW case, and the retry path is documented explicitly:

+	 * hugetlb_wp drops all the locks, but the folio lock, before trying to
+	 * unmap the folio from other processes. During that window, if another
+	 * process mapping that folio faults in, it will take the mutex and then
+	 * it will wait on folio_lock, causing an ABBA deadlock.
+	 * Use trylock instead and bail out if we fail.
 	 */
 	if (need_wait_lock)
 		folio_wait_locked(folio);

Before cycle exists

hugetlb_fault:
  mutex_lock(B)                       [S]
  pagecache_folio = filemap_lock_
        hugetlb_folio(...)   → A     [S]
  folio_trylock(mapped folio)
  hugetlb_wp(pagecache_folio, vmf)
    mutex_unlock(B)   ⇐ window opens
    unmap_ref_private()   (A still held)
    mutex_lock(B)                     [W]

   PG_locked(A) ─────────> fault_mutex(B)
        ^                        |
        +────────────────────────+
   another faulter holds B and waits A

After the folio lock leaves the window

hugetlb_fault:
  mutex_lock(B)                       [S]
  /* no pagecache lookup, no lock A */
  if (write && !writable) {
      folio = mapped folio
      if (!folio_trylock(folio))      → bail,
             need_wait_lock = true       retry
      hugetlb_wp(vmf)
          /* uses folio_test_anon() */
      folio_unlock(folio)
  }
  mutex_unlock(B)
  if (need_wait_lock)
      folio_wait_locked(folio)  ← OUTSIDE the mutex

   fault_mutex(B) ──> PG_locked(A)   only
   no reverse edge  →  no cycle
flowchart LR FM["hugetlb_fault_mutex_table entry"] --> PG["folio lock (PG_locked)"]

After 2ae1ab9934c7: a faulter holding the mutex may still wait for a folio lock, but no one holds a folio lock across a wait for the mutex, the reverse edge is gone together with the pagecache_folio lookup.

Follow-ups in the same series tighten it further(9293fb476552 "mm,hugetlb: sort out folio locking in the faulting path", plus cleanups). In this tree’s mm/hugetlb.c the signature is now static vm_fault_t hugetlb_wp(struct vm_fault *vmf) and pagecache_folio does not exist.

The repeating pattern

Both fixes delete one direction of a two-edge cycle, and neither adds a lock. When you get a DEPT report, the useful question is not "which lock should I add or reorder?" but "which of these two dependencies is unnecessary?", usually it is the one where a long, blocking operation was left inside a lock (ntfs3), or where a lock was held only to answer a question that could be answered without it (hugetlb).

Note on annotation coverage

DEPT can only see what is annotated. The hugetlb case was silent until folio_lock()’s fast path got dept_page_wait_on_bit(). If you suspect a wait/event deadlock and DEPT says nothing, check whether the primitive involved is annotated at all before concluding there is no cycle.

8. When a report is wrong

DEPT is marked EXPERIMENTAL and does produce false positives, because it is tracking dependencies nobody tracked before. The short version of the triage:

  1. Rewrite the summary as edges: X → Y per context. Is the cycle physically possible (can both contexts exist at the same time; are they not boot-only; are they not both readers; is neither a timeout wait)?
  2. Check the class origin of each node. A class printed as <sched> or with (unknown)/(N/A) stacks comes from a code location, not from an object, so ask whether unrelated wait channels pass through that same line. If they do, unrelated dependencies were merged into one node and the cycle may be fabricated.
  3. Inspect /proc/dept_deps for the suspect class: edges arriving from unrelated subsystems are the signature of an over-merged class.
  4. Fix the granularity, not the locking: give the distinct channels distinct struct dept_keys (sdt_map_init_key(), init_completion_dmap()), or separate instances with a subclass (dept_map_init(m, k, sub_u, n)).
  5. Re-verify that real deadlocks are still detected (CONFIG_DEPT_UNIT_TEST, plus the lkdtm folio-lock scenarios if you check in the "lkdtm: Add folio_lock deadlock scenarios" patch), silencing noise by disabling detection is the trap the hugetlb case fell into.

A fully worked example of exactly this, an RCU report where synchronize_rcu() and synchronize_rcu_tasks_trace() shared one key is in fix-false-positive.html.
